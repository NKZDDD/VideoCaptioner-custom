# 需求与执行对应

建模板定义客户的交付结果，软件负责调度。不得把接口、重试次数或内部算法变成客户需要选择的规则。

## 先区分要求的性质

- 硬交付：语言、文字来源、行数、计数口径、固定字号、上下顺序、位置、数字/指定替换、交付格式。须有实际程序执行点；只有模型提示词支持时必须如实说明、提出补齐方案，不能宣称确定性保证。
- 模型文字：自然翻译、语气、语义修正、根据剧本校对专名。传入对应文字阶段，保留上下文；不让模型控制样式和时间。
- 质量目标：不漏台词、名字一致、精确口型等。说明现有证据和验证方法，不把“尚未验收”都做成建模板的阻断项。
- 内部策略：分批、重试、缓存、恢复、分页先后。由软件决定，除非会改变交付效果，不向客户逐项提问。

每条要求记录：来源原话 → 含义/计数例子 → 性质 → 软件字段 → 执行阶段 → 冲突处理 → 验证证据。capabilities.execution_mapping 与 preflight.execution_readiness.routes 是真实字段和路由来源，不凭聊天记忆造映射。未知字段不等于硬要求必然不可实现：先查现有执行器，确实没有执行点才提出缺口。

## 保存前解决冲突

- 保持字号＋固定行数：长句优先拆条；字符数是上限，不代表一定能在该字号放满一行。
- 总行数与每种语言行数要一致；英文两行＋中文一行即合计最多三行。不要继承其他客户的45字符、11字或固定数量。
- “完全沿用剧本”和“以实际语音为准”是不同的文字来源策略，必须先说明差异。不能为了更快，私自互换两者。
- 需要对应剧本、接口和字体是运行条件，不是要求客户每次重建模板。缺输入时在开始前指出具体缺项。
- 如果不能确定客户选“拆条”还是“缩字”、中文数字还是阿拉伯数字、直译参考还是固定译文，主动给出有画面差异的选项并提问。已确认的不要重复问。

## 运行时的恢复边界

统一后处理应复用时间保护、语义分页、标点归属、固定版式、语言角色和导出检查，不推翻已有补丁。

局部可恢复问题只处理失败片段，成功结果保留；有限重试。用户已授权的时间估算只在原句范围内，用“时间待核对”记录，不冒充声学对齐。严格剧本文字来源没有可信匹配时不能悄悄换成原声，缺少必要译文也不能伪造交付；保留恢复材料并明确失败位置。

## 确认与预览

沿用四环节确认。普通句、边界长句、长短不均、相关数字/替换都按这个客户的真实规则展示。预览和任务使用同一份配置和程序；程序、字体或规则变化时重验对应证据。纯静态样式预览不证明ASR、翻译或时码已验收。

检查现有模板时先输出问题及影响，不凭推断改变客户要求、启停状态或文字来源；阿拉伯模板不修改。旧停用草稿不自动启用。确定性的配置修复也需通过同一保存/回读机制，规则含义变化必须主动确认。

## 指定文字规则

明确的指定词替换、去空格与数字写法优先用 capabilities 返回的 program_text_rules 字段。格式为对象：literal_replacements 是 from/to 列表，remove_spaces 是布尔值，number_policy 是 preserve/chinese_only/arabic_allowed/contextual。只记录客户明确指定的原词和目标词，不凭提示词猜扩展辱骂词库，不支持用户正则表达式。重复原词或级联替换必须先解决冲突。语境性辱骂判断仍由模型承担，不能冒充全部程序保证。预览和任务都应用同一份程序文字规则。
